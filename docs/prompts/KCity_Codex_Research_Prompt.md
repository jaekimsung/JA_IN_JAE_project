# K-CITY 후속 연구 계획 및 진행 기록을 위한 Codex 프롬프트

현재 저장소의 K-CITY SUMO 구현을 바탕으로 후속 연구 계획을 구체화하고, 팀원이 Markdown 문서만 읽어도 연구의 목적·현재 상태·다음 작업을 파악할 수 있도록 기록 체계를 만들어줘.

기존 계획을 유지하면서 연구 질문과 실험 설계를 보완하는 작업이다. 새로운 알고리즘 개발이나 다른 시뮬레이터로의 전환을 기본 방향으로 삼지 마라.

**이번 요청에서는 저장소 조사, 필요한 짧은 실행 검증, 후속 연구 계획 구체화, 연구 현황 문서 작성을 수행해라. 본격적인 환경 코드 변경·대규모 학습·1,000만 Transition 수집은 시작하지 마라. 이후 구현과 실험을 요청받으면 아래 문서 기록 규칙을 계속 적용해라.**

## 1. 연구의 목적

개발 목표는 다음과 같다.

> K-CITY의 복합 교통 환경에서 주변 차량·교통신호·목적지 경로를 고려해 안전하고 효율적으로 주행하는 자율주행 의사결정 정책을 개발하고 검증한다.

이를 위한 연구 주제는 다음과 같다.

> K-CITY 복합 교통 환경에서 전문가 사전학습의 효과와 한계 분석
>
> BC 기반 초기화가 PPO의 학습 효율과 교통 수요 변화에 대한 일반화 성능에 미치는 영향을 분석한다.

BC와 강화학습의 결합 자체를 새로운 알고리즘 기여로 주장하지 마라. 본 연구의 기여는 통제된 조건에서 효과와 한계를 비교하고, 조건별 성능 차이와 실패 원인을 재현 가능한 실험으로 설명하는 데 둔다.

‘BC 초기화 PPO가 반드시 더 우수하다’는 결론을 전제하지 마라. 초기에만 유리하거나, 특정 조건에서 불리하거나, 차이를 확인하지 못한 결과도 연구 질문에 답하는 결과로 취급해라.

## 2. 연구 질문과 가설

### RQ1. 전문가 사전학습은 목표 성능에 필요한 강화학습 경험을 줄이는가?

- 비교: PPO-only와 BC 초기화 PPO.
- 확인: 같은 PPO 상호작용 예산에서의 성능, 목표 성능 도달 시점, 초기 실패, 학습 시드 간 변동성.
- 가설 H1: BC 초기화는 기본 주행을 갖춘 출발점을 제공해 초기 실패와 필요한 PPO 상호작용을 줄일 수 있다.
- PPO 상호작용 절감과 전체 비용 절감은 구분한다. 전문가 데이터 생성, BC 학습, PPO 학습 및 평가 비용을 각각 기록한다.

### RQ2. 학습보다 교통 수요가 높아져도 사전학습의 이점이 유지되는가?

- 학습이 끝난 정책을 고정하고 평가 수요를 변화시킨다.
- 기준 수요와 증가 수요에서 안전 수행·완주·위반·대기·실패 유형을 비교한다.
- 가설 H2: BC 이후 PPO가 모방학습 단독 정책의 일부 한계를 보완할 수 있지만, 학습 분포에서 멀어지면 이점이 감소할 수 있다.
- 일반화 범위는 우선 ‘동일한 K-CITY 도로망에서의 교통 수요 변화’로 한정한다. 새로운 도시·실제 도로에 대한 일반화로 확대 해석하지 않는다.

### RQ3. 같은 수량의 전문가 데이터에서 상호작용 상황의 구성이 성능에 영향을 주는가?

- 권장 추가 실험으로 둔다. RQ1·RQ2 수행에 필요한 기반을 먼저 완성한다.
- 같은 전문가 데이터 풀에서 자연 분포 표본과 상호작용 균형 표본을 각각 같은 수량으로 추출한다.
- 가설 H3: 추종·신호 접근과 재출발·차선 변경 등 중요한 상황의 구성이 초기 정책과 후속 PPO 성능에 영향을 줄 수 있다.
- 전문가 정책, 데이터 수, 데이터 생성 조건, 모델 구조, BC 업데이트 예산, 이후 PPO 예산을 통제한다.
- 평가용 증가 수요 데이터를 사전학습에 넣지 마라. 데이터 구성 효과와 평가 조건을 미리 경험한 효과를 섞지 않는다.
- 이 실험은 전문가 실력 차이가 아니라 데이터 상황 구성의 차이를 검증한다.

## 3. 기존 구현부터 확인해라

AGENTS.md 등 적용 지침과 기존 문서를 읽고, Git 작업 상태를 확인해라. 사용자의 미완료 변경사항과 기존 맵·검증 결과를 보존해라.

기존 문서에는 다음 현황이 있다. 이는 확인 대상이지, 현재 구현을 보장하는 사실은 아니다.

- OpenDRIVE 기반 K-CITY 도로망.
- 일반 Edge 176개, 일반 차선 198개, 교차로 내부 차선 346개.
- 일반차량 177대의 유한 투입 시나리오.
- 수요 감응식 신호 14곳.
- Krauss·IDM·EIDM·ACC 차량 거동 모델.
- 여러 교통 조건과 시드에서 누적 2,124대 도착, 충돌·텔레포트 0건.
- K-CITY AV 학습 환경 연결과 BC·PPO 학습은 후속 작업.

다음을 직접 조사해라.

1. 맵 실행·생성·교통 검증 과정과 재현 방법.
2. 실제 SUMO 버전, 시간 간격, 경로, 차량 투입, 신호, 차량 거동 설정.
3. 기존 고속도로 환경과 K-CITY 환경 사이의 연결 상태.
4. reset/step, 관측, 행동, 보상, 종료, 데이터 수집 구현.
5. BC·PPO 코드, 정책 구조, 행동분포, 가중치 호환성과 학습·평가 로그.
6. 정책과 SUMO의 제어 분담, speedMode·laneChangeMode 등 관련 설정.
7. 실제로 재사용할 코드와 수정이 필요한 파일·함수.

결과는 `완료 / 부분 구현 / 미구현 / 문서와 불일치 / 확인 불가`로 구분하고 근거를 붙여라. 문서에만 적힌 내용과 실행으로 확인한 내용을 구분해라.

일반차량 교통 검증, 기존 고속도로 예제 결과, K-CITY 학습 AV 결과를 엄격하게 구분해라. 과거 수치에 맞추기 위해 구현이나 결과를 변경하지 마라.

## 4. 실험 과제와 환경 설계를 구체화해라

### 과제 범위

- 필수 A: 신호 교차로에서 정지·출발·진입 후 지정 경로 주행.
- 필수 B: 다차선에서 주변 차량을 고려해 경로상 필요한 차선 변경.
- 필수 C: 교차로와 다차선 구간을 연속 통과하는 복합 경로.
- 우선 확장: 회전교차로.
- 추가 확장: 긴급차량 양보.

차선 변경 횟수를 늘리는 과제보다 목적지 경로를 위해 필요한 차선 변경을 적절한 시점에 수행하는 과제로 정의해라. 전체 맵에서 임의 주행시키는 것만으로 과제 정의를 대신하지 마라.

### 환경 명세

기존 코드와 연결되는 최소 변경 설계안을 제시해라.

- Episode: 출발·도착·다중 Edge 경로·진행도·충돌·경로 이탈·시간 제한·교착·텔레포트·차량 제거 처리.
- Observation: 자차 속도·차선·진행도, 주변 차량 상대거리·속도, 인접 차선 전후 차량, 신호·정지선 거리, 다음 회전·차선 연결.
- 입력 처리: 관측 범위·주변 차량 수·정렬·누락값·마스킹·단위·정규화·입력 차원.
- POMDP: 전체 상태에서 무엇을 숨기는지 명시. 현재 관측만 사용할지, 관측 누적 등 과거 정보가 필요한지 검토.
- Action: 가감속·차선 유지/변경, 연속·이산 구성, 범위·단위·방향 부호·명령 유지시간·제어 주기.
- 행동 변환: 불가능한 차선 변경, 반복 변경, 교차로 내부 제약, 행동 제한과 PPO log probability의 일관성.
- Reward: 경로 진행·도착 보상, 충돌·신호 위반·위험 행동·불필요한 대기·차선 변경 페널티.
- 정상적인 신호 대기와 불필요한 정지를 구분하고, 계속 정지하거나 위험하게 속도를 높이는 보상 편법을 검토.
- 종료: terminated와 truncated를 과제 정의와 일치시킨다.

미확정 설정은 추천안·선택 이유·변경 가능성을 명시해라. 검증되지 않은 값을 최적값처럼 제시하지 마라.

## 5. 필수 실험 설계

### 실험 A: 학습 방식 비교

비교 대상:

- B0: 전문가 또는 규칙 기반 기준 정책.
- B1: BC-only.
- B2: PPO-only.
- B3: BC 초기화 PPO.

B2와 B3는 정책 구조, 관측, 행동, 정규화, 보상, 교통 조건, 과제 분포, 제어·안전 설정, PPO 업데이트 설정과 상호작용 예산을 맞춰라. 초기화 외의 차이는 반드시 기록해라.

환경 개발 과정에서 작은 과제부터 확인하는 것과 실제 비교 학습의 커리큘럼을 구분해라. 특정 방법에만 다른 과제 순서를 제공해 효과를 혼동하지 마라.

전문가 정책의 성능·한계·사용 정보도 확인해라. 전문가가 특권 정보를 사용하면 이를 명시하고, 정책 관측만으로 모방 가능한지 검토해라.

관찰할 결과:

- 환경 상호작용 횟수에 따른 성능 곡선.
- 검증 집합에서 사전 정의한 목표 성능에 도달하는 시점.
- 정해진 예산 종료 시 최종 성능.
- 학습 초기 실패와 시드 간 변동성.
- 전문가 생성·BC 학습·PPO 학습·평가에 든 비용.

목표를 달성하지 못한 실행은 ‘예산 내 미달성’으로 기록해라. 최종 평가 집합을 모델 선택이나 튜닝에 사용하지 마라.

### 실험 B: 교통 수요 변화

- 기준 투입률을 λ0로 정의하고, 학습은 사전 결정한 기준 조건에서 수행한다.
- 평가: 같은 기준 투입률의 새로운 시드, 증가 수요 1, 더 높은 증가 수요 2.
- 1.5λ0·2λ0는 후보 예시다. 기준 정책으로 수행 가능성을 확인한 후 고정해라.
- 투입률과 실제 차량 밀도·대기열을 구분해 기록한다.
- 초기에는 수요 외에 차량 모델 구성·신호 운영 등 여러 요소를 동시에 바꾸지 않는다.
- 평가 정책은 고정하고 추가 학습하지 않는다.
- 모든 정책이 실패하면 과제의 수행 가능성과 교통 운영 문제도 확인한다.

초기 규모 후보는 학습 방식별 3개 학습 시드, 3개 평가 수요 조건, 학습된 정책·수요 조건별 100개 Episode다. 경로 유형별 배분을 고정한다. 짧은 벤치마크 후 자원에 맞춰 추천 규모를 제시하고, 3개 시드만으로 불확실성이 충분히 해소된다고 주장하지 마라.

### 실험 C: 전문가 데이터 구성

RQ3에 대응하는 추가 실험이다. 같은 수량의 자연 분포 표본과 상호작용 균형 표본으로 BC 초기 정책을 만든 뒤 동일한 PPO 예산으로 비교한다.

상호작용 유형과 표본 추출 기준을 미리 정의해라. 데이터 분리는 Episode·시드 단위로 수행하고, 연속 관측을 사용하는 모델이라면 시간 문맥을 보존해라.

## 6. 평가와 실패 분석

기존 목표는 충돌률 5% 미만, 목적지 완주율 90% 이상, 신호 준수율 100%다. 주행·대기시간도 비교한다. 수업 요구사항 문서가 있으면 기준을 확인해라.

연구의 주요 비교 지표로 다음을 함께 사용한다.

`안전·규칙 준수 완주율 = 시간 제한 내 AV 관련 충돌·신호 위반 없이 목적지에 정상 도착한 Episode 수 / 전체 평가 Episode 수`

이 결합 지표에 기존 완주율 90% 목표를 자동으로 적용하지 마라. 각 지표의 목적과 목표를 별도로 정의한다.

분자·분모, 충돌 범위, 신호 위반 판정, 시간 초과·제거·텔레포트의 실패 처리, 완료된 주행만의 시간 평균에서 생기는 편향을 명시해라.

실패는 추돌·접촉, 신호 위반, 차선 변경, 필수 차선 미확보·경로 이탈, 과도한 대기·시간 초과, 텔레포트·교착 등으로 분류하고 대표 로그·영상으로 확인한다. 이벤트 분류만으로 원인을 단정하지 마라.

주실험의 SUMO 기본 제어·안전 설정은 방법 간 동일하게 유지한다. 요청 행동과 적용 행동, 명시적으로 검출 가능한 보정·거부 사유를 기록해라. 두 행동이 다르다는 이유만으로 모두 안전 개입으로 계산하지 마라.

안전 개입을 분리할 수 없다면 결과를 ‘공통 SUMO 기본 제어·안전 설정을 포함한 시스템 수준 비교’로 해석해라.

검증된 개선, 관찰된 경향, 통계적으로 불명확한 차이를 구분한다. 원래 가설과 다른 결과를 숨기거나 평가 조건을 사후 변경하지 마라.

## 7. 데이터셋과 재현성

1,000만 Transitions 수집 목표는 유지하되 전문가 데이터, 학습 중 데이터, 최종 평가 데이터를 구분한다. 수집 목표와 방법별 학습 예산을 혼동하지 마라.

필수 기록 후보:

- 관측·행동·보상·다음 관측·terminated·truncated.
- Episode·시뮬레이션 시각·시드·경로·시나리오.
- 정책·환경·설정·데이터 버전.
- 요청 행동·적용 행동과 확인 가능한 보정 사유.
- 충돌·도착·시간 초과·위반·텔레포트.

정지 상태 편중, 상호작용 상황의 수량, 누락·중복·시간 정렬을 확인한다. 표준 PPO의 on-policy rollout과 보관용 전체 데이터셋의 활용을 구분한다.

원시 데이터·체크포인트를 Markdown에 넣지 마라. 설정·실행 명령·결과 파일을 연결하고, 저장소 정책에 맞는 위치를 사용해라. 근거 없는 수집 시간이나 저장 용량은 제시하지 말고 측정값과 가정을 구분해라.

## 8. 팀원이 읽을 Markdown 문서 체계

기존에 같은 역할의 문서가 있으면 중복 생성하지 말고 통합해라. 없으면 아래 세 파일을 만든다. 문서는 한국어로 작성하고 저장소 루트 README에 짧은 안내 링크를 추가한다. 기존 README의 주요 내용은 보존한다.

### A. `docs/RESEARCH_PLAN.md` — 무엇을 위해 연구하는가?

안정적인 연구 설계를 담는다.

1. 목적·주제·기여의 범위.
2. RQ1~RQ3와 가설, 각 질문에 대응하는 실험.
3. 필수 범위와 확장 범위.
4. 환경·전문가·학습 방식의 명세.
5. 통제·독립·종속 변수와 데이터 분리.
6. 지표 정의, 예산, 시드, 평가·모델 선택 절차.
7. 단계별 구현 계획과 완료 기준.
8. 미확정 사항, 추천 결정, 근거와 참고 문헌.

구현 계획에는 `작업 ID / 목적 / 선행 조건 / 실제 수정 대상 파일·함수 / 검증 방법 / 완료 기준 / 산출물 / 우선순위 / 예상 작업량` 표를 포함한다.

일상적인 작업 이력은 이 문서에 계속 쌓지 마라. 연구 설계를 바꾸면 변경 이유와 영향을 현황 문서의 결정 기록에도 남겨라.

### B. `docs/RESEARCH_STATUS.md` — 지금 어디까지 했는가?

팀원이 가장 먼저 읽는 현황 문서다. 상단만 읽어도 현재 상황을 이해할 수 있어야 한다.

다음 구조를 사용해라.

1. 마지막 갱신 시각: 실제 갱신 시각을 시간대가 포함된 ISO 8601 형식으로 기록.
2. 현재 단계, 이번에 완료한 일, 가장 중요한 확인 결과, 막힌 일, 바로 다음 작업을 짧게 요약.
3. 단계별 상태표: `작업 ID / 작업 / 상태 / 확인 근거·산출물 / 관련 파트 / 다음 행동`.
4. 현재 확인된 결과: 실험 ID와 결과 링크 포함. 기존 일반차량 검증과 AV 학습 성과를 분리.
5. 미확정 사항·문제·의존관계: 영향과 해결할 다음 행동 포함.
6. 다음 작업 3~5개: 우선순위·선행 조건·완료 기준 포함.
7. 결정 기록: 날짜·결정·이유·다른 대안·영향·관련 실험 ID.
8. 날짜별 작업 기록: 수행한 일·검증·결과·다음 작업을 간결하게 누적.

상태는 `미착수 / 진행 중 / 검증 대기 / 완료 / 차단 / 보류`로 통일한다. 코드 작성만 끝난 상태를 검증 완료로 표시하지 마라. 근거 없는 전체 진행률 퍼센트는 사용하지 마라.

상단 요약은 현재 상황에 맞게 갱신하고, 아래의 날짜별 기록과 중요한 결정은 보존한다. 변경이 없는 과거 설명을 매번 복사하지 마라. 사람이 적은 메모를 임의로 삭제하지 마라.

### C. `docs/EXPERIMENTS.md` — 무엇을 어떻게 실험했고 무엇을 얻었는가?

실험 실행과 결과의 인덱스를 유지한다. 실험마다 고유 ID를 부여하고 상태를 `계획 / 실행 중 / 완료 / 실패 / 중단 / 무효`로 구분한다. 실패·중단·무효 실행도 삭제하지 마라.

요약표는 다음을 포함한다.

`실험 ID / 연결된 RQ·가설 / 정책·비교 조건 / 상태 / 주요 결과 / 설정·로그·결과 링크 / 해석·제한`

각 실험의 상세 기록 또는 연결된 설정·결과에는 다음이 있어야 한다.

- 목적, 변경 변수, 고정 조건, 성공·실패 판정 기준.
- 코드 커밋과 작업 트리 변경 여부. 커밋이 없으면 설정·차이 파일 등 대체 식별 근거.
- SUMO·학습 환경·정책·전문가 데이터 버전.
- 학습 시드·평가 시드·경로·교통 수요·안전 설정.
- BC 데이터 수·학습 예산, PPO 상호작용 수·예산.
- 실행 명령, 시작·종료 시각, 실행시간, 완료 여부.
- 평가 Episode 수, 지표·단위·변동성·실패 유형.
- 로그·체크포인트·데이터·영상·원시 집계 파일의 저장소 상대 경로.
- 관찰 사실, 해석, 제한, 가설 지지 여부를 구분한 결론.

실행 전에는 계획과 설정을 기록하고, 종료 후 실제 실행 조건과 결과로 보완해라. 설정을 바꿔 다시 실행하면 새 실행 ID를 사용하고 이전 기록과 연결해라.

계획된 실험에 결과 수치를 채워 넣지 마라. 결과가 없으면 `미실행` 또는 `측정 전`으로 표시한다. 대규모 로그·원시 표는 별도 파일에 저장하고 Markdown에는 요약과 링크를 둔다.

## 9. 이후 모든 작업에서 지킬 기록 규칙

- 작업 시작 전 RESEARCH_PLAN과 RESEARCH_STATUS를 읽고 이전 진행 상황에서 이어간다.
- 작업 시작 시 해당 작업을 진행 중으로 표시하고, 종료 시 검증 결과와 다음 행동을 갱신한다.
- 장시간 실험은 실행 ID·설정·현재 진행 상태를 남겨 다른 사람이 중복 실행하지 않게 한다.
- 코드·설정 변경이 어떤 RQ와 실험에 필요한지 연결한다. 연구 목적과 무관한 기능 확장을 피한다.
- 버그 수정 전후 실험이 비교 불가능해졌다면 이전 결과를 무효 또는 참고용으로 표시하고 이유를 남긴다.
- 시뮬레이터 기본 안전 기능이 바뀌면 비교 가능성에 미치는 영향을 기록한다.
- 중요 설계 변경은 이전 계획을 조용히 덮어쓰지 말고 이유·영향·관련 결과를 남긴다.
- 확인한 사실, 해석, 가정, 추천, 미확정 사항을 구분한다.
- 수행하지 않은 실험, 확인하지 않은 코드 동작, 기대 성능을 완료 결과처럼 쓰지 않는다.
- 팀원이 이해할 수 있는 설명을 먼저 쓰고 필요한 파일·함수·명령을 연결한다. 내부 로그만 나열하지 않는다.
- 문서 링크·실행 명령·결과 경로가 실제와 일치하는지 확인한다.

## 10. 이번 요청의 최종 산출물

1. 실제 코드·설정·로그에 근거한 현재 상태 진단.
2. 기존 계획을 구체화한 RESEARCH_PLAN.md.
3. 실제로 확인한 상태만 담은 RESEARCH_STATUS.md.
4. 기존 검증과 향후 실험을 구분한 EXPERIMENTS.md.
5. README의 문서 안내 링크.
6. 바로 다음에 수행할 작업 5개와 첫 구현 작업의 완료 기준.

마지막 응답에는 현재 단계, 확인한 사실, 추천 연구·개발 순서, 핵심 미확정 사항, 작성한 문서 링크를 간결하게 제시해라.

저장소에서 알 수 있는 내용은 먼저 조사하고, 선택 가능한 대안만 나열하지 말고 과제 규모와 기존 코드에 맞는 추천안을 제시해라. 연구의 큰 방향을 임의로 바꾸지 말고 변경이 필요하면 근거와 영향을 명시해라.
